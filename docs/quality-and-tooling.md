# Quality & tooling

How this template keeps itself honest: what runs, why each tool exists, and
the production-facing guards that don't fit naturally into `testing.md` (about
the test suite) or `architecture.md` (about module boundaries).

```bash
ruff check .   # lint
mypy           # type check
lint-imports   # architecture boundary contracts (also runs inside pytest)
pytest         # tests
```

`.github/workflows/ci.yml` runs exactly these four on every push/PR, plus a
second job that applies Alembic migrations against a real PostgreSQL service
container — see [CI pipeline](#ci-pipeline) below. `pre-commit` runs the first
three locally, before you even push — see [Pre-commit hooks](#pre-commit-hooks).

## Type checking (mypy)

`mypy.ini` scopes checking to `files = app` — the application code, not
`tests/`. Module-owned tests under `app/modules/*/tests/` happen to fall
inside that scope too (they're physically under `app/`), so they get checked
as a side effect of following imports, but `tests/` at the repo root and the
root `conftest.py` don't. That's a deliberate line, not an oversight: mypy
earns its keep fastest on the code that ships, and a test suite that's
already green under `pytest` has a different, complementary kind of coverage.

### Why every `Result`-returning call site uses `.unwrap()`/`.unwrap_err()`, not `.ok()`/`.err()`

The `result` library types `Ok.ok()`/`Err.err()` per-subclass rather than via
a `TypeGuard` on the shared `.is_ok()`/`.is_err()` instance methods, so mypy
can't narrow `Result[T, E]` after the `if result.is_err(): ...` checks this
codebase uses everywhere — `.ok()`'s inferred type stays `T | None` even on a
branch that's already proven not-`None` at runtime. Every router, facade, and
`public_api.py` in this template was rewritten from `.ok()`/`.err()` to
`.unwrap()`/`.unwrap_err()` for exactly this reason: `Ok.unwrap() -> T`,
`Err.unwrap() -> NoReturn`, and a union with `NoReturn` collapses to just `T`,
so mypy narrows correctly with no `# type: ignore` needed anywhere in that
call chain. As a bonus, `.unwrap()` fails loudly with `UnwrapError` instead of
silently returning `None` if a future edit ever removes the guarding
`is_err()`/`is_ok()` check by mistake — a stricter failure mode than the one it
replaced. See [architecture.md](architecture.md#result-pattern-over-exceptions)
for the Result pattern itself.

### Third-party stubs

`types-passlib` is installed alongside `mypy` in `requirements.txt` specifically
because `passlib.context` ships no type information of its own — without it,
`mypy` reports `import-untyped` on `app/shared/security.py`. Every other
third-party dependency in this template (FastAPI, SQLAlchemy, Pydantic, PyJWT,
slowapi) ships its own types or has good-enough inline stubs, so
`ignore_missing_imports` is deliberately **not** set globally in `mypy.ini` —
that would also hide a genuine typo in a first-party import path, not just a
missing third-party stub.

## Pre-commit hooks

`.pre-commit-config.yaml` defines three `local` hooks — `ruff`, `mypy`,
`lint-imports` — using `language: system`, which means they invoke whatever
`ruff`/`mypy`/`lint-imports` executables are already on `PATH` inside your
active virtualenv, rather than pre-commit managing its own separate,
independently-versioned toolchain. That's deliberate: this template already
pins tool versions in exactly one place, `requirements.txt`; a second pinned
version inside `.pre-commit-config.yaml` (the more common pattern, using
`repo: https://github.com/astral-sh/ruff-pre-commit` and similar) would give
CI and your local pre-commit run two independent opportunities to drift out of
sync with each other.

Install once per clone:

```bash
pre-commit install
```

After that, all three hooks run automatically on `git commit`, against the
files you changed.

### A gotcha this repo already ran into: `ruff`'s hook has to ignore filenames too

`ruff.toml` excludes `alembic/versions` from linting (`extend-exclude =
["alembic/versions"]`) — those files are Alembic-generated, not meant to pass
this project's style rules. `ruff check .` (a bare directory scan, which is
what CI runs and what `mypy`/`lint-imports`'s hooks above already do via
`pass_filenames: false`) respects that exclude. But pre-commit's *default*
behavior for a hook is to pass it the specific list of changed/staged file
paths as arguments — and `ruff check <explicit-path>` does **not** apply
`extend-exclude` to a path you handed it explicitly; excludes only apply to
implicit directory discovery. The first version of the `ruff` hook here used
that default, and passed as soon as you ran `pre-commit run --all-files` on a
repo whose Alembic migrations hadn't changed — then failed the moment someone
touched `alembic/versions/orders/...`, flagging five style violations in
autogenerated code nobody was meant to hand-edit to satisfy `ruff`.

The fix: `entry: ruff check .` (the literal directory argument, not a
filenames placeholder) plus `pass_filenames: false`, so the hook always runs
the same bare directory scan CI does — files list and excludes included.

## CI pipeline

Two jobs, both defined in `.github/workflows/ci.yml`:

- **`lint-and-test`** — `ruff check .`, `mypy`, `lint-imports`, `pytest`, in
  that order, against SQLite (the default `DATABASE_URL`). This is the fast
  feedback loop; it never touches a real database server.
- **`postgres-migrations`** — spins up a real `postgres:16-alpine` service
  container and runs `alembic upgrade head` against it. This exists because
  the schema-per-module path (see
  [database.md](database.md#schema-per-module-isolation-postgresql)) and the
  cross-schema foreign key it produces are **PostgreSQL-only behavior** —
  SQLite's `module_schema()` always resolves to `None`, so the first job's
  SQLite-backed test run can't exercise this path at all. Every push gets a
  real, disposable Postgres instance instead of relying on someone
  remembering to check this by hand before a release.

## Production readiness guards

Two things this template refuses to let you ship by accident, both enforced
in code (not just documented and hoped-for):

### `JWT_SECRET_KEY` can't stay the default in production

`app/shared/config.py`'s `Settings` has a `model_validator(mode="after")`:

```python
@model_validator(mode="after")
def _forbid_default_jwt_secret_in_production(self) -> "Settings":
    if self.APP_ENV == "production" and self.JWT_SECRET_KEY == _DEFAULT_JWT_SECRET_KEY:
        raise ValueError(...)
    return self
```

`Settings()` is constructed at import time (`app/shared/config.py`'s last
line), so this isn't a runtime check somewhere deep in a request path — set
`APP_ENV=production` without also overriding `JWT_SECRET_KEY`, and the
process fails to even start, whether that's `uvicorn app.main:app`, a test
importing `app.main`, or anything else that imports the settings module.
`.env.example`'s `JWT_SECRET_KEY` placeholder is deliberately the exact same
string as the Python-level default (`dev-secret-key-change-in-production`),
not a different-looking placeholder — so copying `.env.example` to `.env`
verbatim and forgetting to edit it still trips this guard in production,
rather than silently working with a secret every clone of this template
shares. See `tests/test_config.py` for the regression tests pinning this
down.

### The rate limiter doesn't survive more than one process

`app/shared/rate_limiter.py`'s `Limiter` (`slowapi`) keeps its request
counters in a single process-wide in-memory store. That's exactly right for
local dev and for the test suite (see
[testing.md](testing.md#a-gotcha-this-suite-already-ran-into-the-rate-limiter-is-process-wide)
for the test-isolation angle) — and exactly wrong the moment you run more than
one process. Multiple `uvicorn`/`gunicorn` workers, or multiple container
replicas behind a load balancer, each keep independent counters: a client's
requests can land on any worker, and each worker only knows about the
requests *it* personally handled. `/api/v1/users/register`'s `10/minute`
quietly becomes `10 × (worker count)/minute` in aggregate — not a crash, not
an error in the logs, just a rate limit that's weaker than its configured
number implies.

This template does not implement the fix, on purpose — it would mean adding a
Redis dependency (a service to run, a `REDIS_URL` to configure) that most
single-instance deployments of this template don't need. If you scale past one
process, `slowapi` already supports a Redis-backed `storage_uri` for
`Limiter(...)`; swapping it in is a configuration change to
`rate_limiter.py`, not a redesign.

## Known gaps, kept deliberately

Not every rough edge here is unaddressed by accident. Documented here so
"why hasn't this been fixed" has an answer instead of looking like an
oversight:

- **Rate limiter has no distributed backend** — see above. Single-process
  deployments (which is what this template ships as, via its `Dockerfile`)
  are unaffected; scaling out requires the Redis swap described above.
- **Facade fakes only cover `UnitOfWork`-free methods** —
  `tests/test_facade_fakes.py` covers `UserProductFacade.get_user_with_products`,
  the one facade method with no `UnitOfWork`. `create_product_for_user` and
  `OrderFacade.place_order` both open one internally, which needs a real (even
  if in-memory) database session — faking that would mean monkeypatching the
  session factory, which defeats the point of a fake-based test. See
  [architecture.md](architecture.md#protocol-based-module-contracts).
- **`alembic/versions/111c01eef9d1_initial_schema.py` bundles two modules** —
  it predates the per-module migration directory split
  ([database.md](database.md#per-module-migration-directories)) and mixes
  `users` and `products`' original tables in one revision. It's left as-is
  rather than split into two revisions, because that would rewrite a revision
  ID already recorded in any real database's `alembic_version` table —
  breaking `alembic upgrade`/`downgrade` for every existing deployment, for a
  purely cosmetic gain.
